# face 콕 — 테스트 / 장애대응

정리 기준일: 2026-09-03

이 문서는 무엇을 테스트해야 하는지, 그리고 행사 기간(2026.09.30~10.02) 중
장애가 나면 어떤 원칙으로 대응하는지를 정리한다. 인프라 구성 자체는
[인프라설계.md](./인프라설계.md)를 따른다 — 이 문서는 그 위에서의 검증·대응
절차만 다룬다.

## 1. 테스트 범위

| 계층 | 방법 |
| --- | --- |
| 프론트 | 로컬에서 화면별 mock 데이터 기준 수동 확인 |

## 2. 기능별 우선순위 테스트 케이스

행사 성격상(3일, 실시간, 동시 접속) 아래는 특히 경계값·동시성 문제가 나기
쉬운 지점이다.

- **콕**: 하루 3회 제한이 KST 자정 기준으로 정확히 리셋되는지, 같은 상대
  중복 발송 차단, 시간 만료 없음, 상호 콕 시 즉시 매칭 성사
- **채팅**: 운영시간(09:00~18:00) 경계 시각 처리, `client_message_id`로
  재전송 시 중복 저장 안 되는지, 서버 재연결 후 메시지 순서
- **신고/영구정지**: 정지 처리 즉시 로그인·콕 발송·매칭·채팅이 전부
  차단되는지 (부분적으로만 막히는 경우가 없는지)
- **미션**: STEP이 정확히 순차로만 공개되는지, 관리자가 완료 처리한 순간
  참가자 화면에 즉시 반영되는지

## 3. 장애 등급

| 등급 | 정의 | 예시 |
| --- | --- | --- |
| 심각 | 서비스 전체 접속 불가 | 로그인 자체가 안 됨, ALB/전체 EC2 다운 |
| 부분 | 특정 기능만 동작 안 함 | 채팅만 안 되고 나머지는 정상 |
| 경미 | 기능은 되지만 화면/경험 문제 | UI 깨짐, 알림 지연 |

## 4. 1차 대응 원칙

- **EC2 한 대 장애** — ALB 헬스체크가 자동으로 감지해서 신규 연결을 나머지
  한 대로 돌린다. 기존에 연결돼 있던 사용자는 끊기고 클라이언트가
  재연결해야 한다 ([인프라설계.md](./인프라설계.md) 10번)
- **RDS 장애** — Single-AZ라 자동 failover가 없다(SPOF로 감수한 상태).
  장애 시 스냅샷에서 수동 복구해야 하며, 복구 소요 시간 동안 서비스가
  멈춘다는 걸 전제로 한다. ALB는 `/actuator/health/liveness`(앱 자체 상태만)를
  보므로 DB가 멈춰도 앱 서버는 교체되지 않고, DB가 돌아오면 바로 다시
  처리한다(#145)
- **Redis 장애** — ElastiCache 한 대라 자동 failover가 없다. Redis 명령은 1초만
  기다리고 실패로 넘어간다(`spring.data.redis.timeout`, #147). 멈춘 동안: 채팅은
  DB에 저장되고 보낸 사람은 약 2초 뒤 응답을 받지만 상대방 실시간 전달은 멈춘다
  (FE 20초 이력 조회로 채워지고, Redis가 돌아오면 밀린 전달이 한꺼번에 간다).
  새 채팅 소켓 연결은 약 1초 걸린다. 회원가입 인증 코드는 저장되지 않아 가입이
  안 된다. 콕·매칭·프로필은 영향 없다. Redis가 돌아오면 바로 정상으로 돌아온다
- **배포 직후 장애** — 배포한 버전에서 바로 문제가 확인되면 즉시 이전
  버전으로 롤백한다. 구체적 롤백 절차(이미지 태그 관리 등)는 CI/CD 구성
  시점에 확정한다

## 5. 모니터링 · 백업
